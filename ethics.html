Ethics and privacy reflection

A study planner collects information about a person's workload, deadlines and habits, which is more personal than it first looks. This page sets out the design decisions that limit what StudyDeck collects, keeps that data on the device it was typed on, and gives the user control over it.

What the application collects, and what it refuses to collect

The ethical starting point is data minimisation: collect only what the task list cannot work without. A task stores a title, a course code, a course name, a due date, a description and optional notes. That is all. The application does not ask for an email address, a phone number, a student number, a photo or a location, even though the home page could have displayed them.

Two further limits are built into the code rather than written into a policy:

  • No account, no server. There is no sign-up form, no database and no API call anywhere in the project. Tasks are written to localStorage on the device that typed them, so the data is never transmitted and there is nothing to leak from a remote store.
  • No third-party requests. Fonts, styles, scripts and images are all bundled with the project. The pages load no analytics service, no advertising network, no embedded tracker and no external CDN, so opening the site tells nobody else that it was opened.

Features that protect privacy

A login gate

The task list sits behind a username and password, so opening the laptop in a lecture theatre does not expose someone's deadlines to the person in the next seat.

Session-only sign-in

The session flag lives in sessionStorage, which is emptied when the browser tab closes. A shared computer therefore does not keep the list open for the next person.

No hidden persistence

Nothing is stored beyond the task list itself: no preferences, no history, no identifier. Clearing the browser's storage for this site removes every trace of the work.

Visible control

Every task can be edited and deleted, deletion asks for confirmation first, and the sign-out button is always on screen while the list is open.

How this shows up in the code

Example 1 · Input validation as a duty of care

Bad input is rejected before it is stored, and the message explains what to do instead of blaming the user. A past due date, an empty title or a course code that is not in the form INFO1012 never reaches localStorage. This protects the user's own data quality: a list full of impossible dates is worse than no list, because the student starts trusting a tool that is wrong. 

var days = daysFromToday(data.dueDate);
if (days < 0) {
  fail('dueDate', 'The due date cannot be in the past. Choose today or a later date.');
}

Example 2 · A login gate that is honest about its limits

The credentials are checked in js/auth.js, and the code comments state plainly that a static site cannot keep a secret: anyone who opens the file can read the password. The gate is presented as a barrier against a casual onlooker, not as security against an attacker. Claiming more would be the unethical choice, because it would invite someone to store genuinely sensitive information behind a lock that does not exist.

Example 3 · Data the application deliberately does not keep

Task notes are capped at 200 characters and no field asks for personal details. The point is not to make the app less useful; it is to make the stored record small enough to be obviously harmless if the device is lost or borrowed.

Example 4 · Accessible by default

Every form control has a visible label, error messages are announced through role="alert", the current time updates in a live region, focus is visible on every control, and the layout works at 375px wide. An application that only works for users with a mouse and perfect eyesight excludes people for no reason, which is an ethical failure before it is a technical one.

Where this sits against privacy principles

The Australian Privacy Principles (APPs) in the Privacy Act 1988 are the reference point taught in the Week 8 tutorial. Three of them map directly onto this project:

  • APP 1 - open and transparent management. The application tells the user, on the task page itself, that tasks are stored on this device only, rather than burying that in a policy nobody reads.
  • APP 3 - collection of solicited personal information. Only information necessary for the stated purpose is requested: there is no field that exists for future marketing or analytics.
  • APP 11 - security of personal information. The effective measure here is not encryption but elimination: data that is never transmitted cannot be intercepted, and a session-scoped sign-in limits who can see it on a shared machine.
The strongest privacy control in StudyDeck is that most data a planner could collect simply never leaves the browser: no account, no upload, no third party.

Known limitations, stated plainly

The design is not a claim of security. Three limits are worth recording:

  • The login check runs in the browser, so it can be bypassed by anyone who reads the source or edits the page. A real deployment would move authentication to a server and never ship the password to the client.
  • Tasks are stored unencrypted in localStorage. Anyone with access to the browser profile on that device can read them, which is why the application asks for no personal details in the notes field.
  • There is no export or backup, so clearing the browser's data destroys the list. A future version would add a JSON export so the user, not the application, holds the copy.

Each of these is a place where the honest design is to state the limit and keep the collected data small, rather than to imply protection that the implementation cannot provide.
